# Twill: project notes

Twill is an SMS/MMS app forked from GrapheneOS Messaging (Compose rewrite, v13+). The name is a weave; the long-term plan is to add other messaging protocols alongside SMS/MMS.

## Rules

- **Every build type must install alongside the system Messaging app, never replace it.** Release builds are `app.twill.messages` (set in `androidComponents` in `app/build.gradle.kts`); `defaultConfig.applicationId` stays `app.twill`, so perf is `app.twill.perf` and debug `app.twill.debug`. Never set it back to `com.android.messaging`, and never add anything that only works under that package name.
- The Kotlin/Java source package and Gradle `namespace` stay `com.android.messaging`. Renaming them would make every upstream merge conflict.
- The app's display name is "Twill" (`app_name` in `res/values/strings.xml`); debug builds are "Twill d" (set in `app/build.gradle.kts`).
- Privacy-affecting options (anything that contacts a third party) default to **off**, like the YouTube and website link previews.
- Keep edits to upstream files small; put new code in new files where possible, so `git merge upstream/main` stays easy.
- New strings go in `res/values/strings.xml` (English only for now; other locales fall back to it).

## Remotes and building

- `origin` = github.com/jawsh207/twill, `upstream` = github.com/GrapheneOS/Messaging.
- `.github/workflows/build-apk.yml` runs on every push and on manual dispatch. From a cloud session: `gh workflow run build-apk.yml -R jawsh207/twill --ref main`, then poll `gh run view <id> -R jawsh207/twill --json status,conclusion`.
- CI uploads `twill-apk` (perf build: release config with R8, `app.twill.perf`, label "Twill") for everyday use and `twill-debug-apk` (`app.twill.debug`, "Twill d"). Debug builds are unoptimized and coverage-instrumented, so they stutter; judge performance only on the perf build. Test builds are signed with the committed `.github/ci/debug.keystore` (force-added; `*.keystore` is gitignored) so they update each other.
- Real releases: `.github/workflows/release.yml` (manual dispatch only) builds `assembleRelease` (`app.twill.messages`) signed with the private key from repository secrets (`TWILL_KEYSTORE_BASE64`, `TWILL_KEYSTORE_PASSWORD`, `TWILL_KEY_ALIAS`, `TWILL_KEY_PASSWORD`), verifies it isn't debug-signed, and publishes GitHub release `v<versionName>` with the APK and its SHA-256. It refuses to reuse a version or release one without notes: before each release bump `versionCode`/`versionName` and add a `## <versionName>` section to `CHANGELOG.md` (user-facing, newest first), which becomes the release page's "What's new". Add changelog lines as features land, so the next release's section is ready. Never commit or print the key.
- Cloud sessions usually can't reach Google's Maven repo, so they can't compile locally. Use the workflow to verify builds, and run `ktlint` on changed Kotlin files before pushing.

## Where Twill's features live

- **Settings structure:** top-level Settings (`SettingsNavKey`) is `ui/appsettings/twill/TwillSettingsScreen.kt`: one entry per protocol (SMS Settings, Nostr Settings, Delta Chat Settings) plus app-wide items (open source licenses). Everything upstream showed as top-level Settings now lives under `SmsSettingsNavKey` in `SettingsNavEntries.kt`. When adding a new protocol, give it its own entry on `TwillSettingsScreen` and its own settings pages, and keep app-wide items on the top level.

- **Boolean settings:** `AppBooleanPref` enum + keys/defaults in `res/values/constants.xml`; read in `AppSettingsRepository`; UI in `ui/appsettings/general/ui/AppSettingsScreen.kt` and `ui/appsettings/privacy/ui/PrivacySettingsScreen.kt`. Code that can't suspend reads prefs through `AppPreferenceReader`.
- **Delay sending:** `ConversationDraftDelegateImpl.sendDraftAfterDelay` (3 s, application scope, cancel via `cancelDelayedSend`) publishes `delayedSend` state; `ConversationScreen.kt` turns it into `LocalDelayedSendUi`, and `ConversationSendActionButton.kt` draws the countdown ring with an X that cancels.
- **Settings placement:** "Delay sending" (first in Advanced) and "Send long messages as MMS" (last in MMS) live on the per-SIM Advanced page, `SubscriptionSettingsScreen.kt`, fed by `AppSettingsViewModel` in `SettingsNavEntries.kt`. They are app-wide prefs, so every SIM's page shows the same values. "Keep unread at top" stays on the main Settings page.
- **Scheduled messages:** storage in `data/scheduled/ScheduledMessageStore.kt` (JSON in private SharedPreferences); alarms and sending in `ScheduledMessageScheduler.kt`; `receiver/ScheduledMessageReceiver.kt` handles the alarm, boot and app update; UI in `ui/conversation/scheduled/`, opened by long-pressing the send button. Pending messages show as a clock-with-count in the conversation top bar (`ScheduledMessagesIndicator.kt`, injected via `LocalConversationTopBarExtraActions` between the call button and the 3-dot menu); tapping it lists them with cancel buttons. `ConversationScreen.kt` builds `LocalSendLongPressActions` (Schedule message, plus Switch SIM on multi-SIM phones); `ConversationComposeBar.kt` runs a single action directly or shows a menu for several. Schedule only appears where `LocalScheduledMessagesController` is provided (`ConversationNavEntries.kt`); without it the long press keeps upstream behaviour (SIM selector).
- **Keep unread at top:** `ConversationListOptimisticSnapshotDelegate.withUnreadOnTop` (pinned first, then unread).
- **Website link previews:** `ui/conversation/messages/ui/link/WebLinkPreview.kt` (HTTPS-only fetcher with size/time limits and an in-memory cache); URL picked in `ConversationMessageContentBuilder.kt`; card shown in `ConversationMessageBubble.kt`.
- **Protocols other than SMS (shared layer, `twill/`):** every extra protocol implements `TwillProtocol` (`twill/TwillProtocol.kt`: chats, messages, details, send/sendFile, read/pin/delete, requests, new chat/group, avatars, `syncOnce`, `setKeepConnectedInBackground`) and is registered in `TwillProtocolsModule` (`twill/TwillProtocols.kt`). Ids are strings chosen by the protocol. Everything else is shared and written once:
  - UI in `ui/twill/`: inbox sections (`inbox/`, one collapsible section per enabled protocol via `LocalTwillInbox`, provided in `ConversationListNavEntries.kt`, and the optional `sections` parameter of `ConversationListItems`), the chat screen (`chat/TwillChatScreen.kt`, opened with `TwillChatNavKey(protocol, chatId)`), `TwillAvatarImage`.
  - `TwillRuntime` (`twill/TwillBackground.kt`): `start(markVisible)` from every screen/background entry point; one foreground service (`TwillConnectionService`, one notification) for all "always connected" protocols, one 15-minute job (`TwillSyncJobService`), one boot receiver.
  - `TwillAppVisibility`: on-screen tracking (with a 30 s grace for connections) and the open chat, so it doesn't notify.
  - `TwillNotifications`: one message channel and small icon per protocol (`<key>_messages`; icons `ic_notification_nostr`, `ic_notification_deltachat`, and `ic_notification_sms` for SMS/MMS: the same speech bubble with a different cut-out, also used in the new-chat menu; upstream's `ic_sms_light` is no longer referenced; the conversation list's Start chat button uses `ic_start_chat`, the same bubble with a plus). The launcher icon (`ic_launcher_foreground` / `ic_launcher_monochrome`, blue `#1565C0` background) is two of the same bubbles overlapping, the back one mirrored and cut by a clip path. Tapping opens the chat via `twillChatRoute` in `MainActivity`.
  - Adding a protocol: implement `TwillProtocol`, bind it in `TwillProtocolsModule`, add its id to `TwillProtocolId`, a channel name in `TwillNotifications`, a notification icon, and a settings entry.
- **Nostr (NIP-17 DMs):** library is Quartz (`com.vitorpamplona.quartz`; read its source on GitHub at the matching tag for exact APIs). Code in `nostr/`: `NostrProtocol` (the `TwillProtocol` adapter), `NostrAccountStore` (account, relays, delivery mode; local key encrypted by `KeystoreCipher`), `NostrSignerProvider` (Amber via `NostrSignerExternal`, or `NostrSignerInternal`; screens host Amber prompts with `NostrForegroundHost()`), `NostrMessageStore` (own SQLite DB `nostr.db`), `NostrMessenger` (relay client, gift-wrap receive/send, profiles/NIP-05, notifications). Chats are identified by a chat key (`NostrChatKey`): the other person's hex key for one-to-one, or `g:` + the other members' sorted keys for groups. `NostrMedia` handles Blossom uploads, encrypted attachment downloads and cached profile pictures. Anything that contacts a third party (pictures, auto-download) is an `NostrAccountStore` toggle that defaults off. `NostrMessageStore` is SQLite version 2; add new versions with an `onUpgrade` step. Settings in `ui/nostr/settings/`.
- **Delta Chat:** the official core (chatmail core) is built from source by `scripts/build-deltachat-core.sh` (version + commit pinned there; needs Rust and the NDK; 15-30 min, cached in CI by `build-apk.yml`) into one library, `deltachat/jniLibs/arm64-v8a/libtwill_deltachat.so` (gitignored): Twill's JNI bridge (source `native/deltachat/twill_deltachat_jni.c`) with the core's static library linked in. Only the bridge's `Java_*` functions are exported, so the linker drops the core code Twill never reaches (mostly its C API), and relocations are packed (RELR); that's about 2 MB smaller than shipping the core's own `libdeltachat.so`. It's loaded in-process straight from the APK (not extracted). The core has no build switches for optional parts (iroh peer-to-peer, used for live webxdc and second-device setup, is about 0.7 MB of code but can only be removed by patching its source). `DeltaChatRpc` calls the core's JSON-RPC API through `dc_jsonrpc_blocking_call` (method names and types: `deltachat-jsonrpc/src/api.rs` in github.com/chatmail/core at the matching tag; params are positional) and reads events from the core's event emitter (`DeltaChatEvents` = DC_EVENT_* ids). It frees the core after a minute idle unless `keepRunning` (network wanted); calls hold a read lock, shutdown a write lock. `DeltaChatProtocol` maps it to `TwillProtocol` (chat ids = core chat ids): events invalidate a message cache and trigger per-chat reloads (only new or changed messages are fetched), turns `IncomingMsg` into notifications, runs IO while visible or always-connected, and has setup helpers (`createProfile`, `setupFromCode`, `setupWithEmail`, `removeProfile`, `inviteLink`). `DeltaChatAccountStore` remembers the core account id, whether setup finished (Delta Chat is off until then), and the delivery mode. Settings in `ui/deltachat/settings/`. Without the library the build still works and Delta Chat Settings says it isn't included. Upgrading the core: bump `VERSION` and `COMMIT` in the script and the version in the licenses notice (`messaging.licenses.gradle.kts`).
- **SMS on/off:** `twill/TwillSms.kt` (pref `twill_sms`/`enabled`, default on). Off means: `ShouldShowOnboarding` returns false (no SMS role/permission prompts), no phone-number prompt, the inbox hides the SMS section (`ConversationListSections.isSmsHidden`) and shows a setup hint when nothing else is set up, and the new-message button opens a protocol picker (`TwillInbox.isNewChatPickerVisible`, wired in `ConversationListNavEntries.kt`). With SMS on, a normal press starts SMS as upstream and a long press opens the same picker with an SMS/MMS row first (`ui/twill/inbox/TwillStartChatLongPress.kt`: `rememberStartChatLongClick` + `Modifier.twillLongPress`, hooked into upstream's `StartChatFab`; no long press when no other protocol is set up). Turning SMS off saves the choice immediately (`disable()`); SMS components (deliver receivers, quick-reply service, sms: links, share target) are disabled by `TwillSms.applyComponents` only once Twill isn't the default SMS app, re-checked on every resume (`BugleActivityUtil.onActivityResume`) and at `TwillRuntime.start`. With SMS off (or on but before onboarding has restored permissions), nothing upstream that needs SMS/phone permissions may run: the resume-time SMS sync is skipped, and SMS Settings shows only the switch (upstream's page reads the SIM count, which needs READ_PHONE_STATE). UI: "Use Twill without SMS" on both onboarding steps; "Use Twill for SMS/MMS" switch as the first row of SMS Settings (`ui/twill/TwillSmsSwitch.kt`, injected into upstream's two SMS settings lists via `LocalSmsSettingsHeader`; with SMS off, SMS Settings shows only the switch, `SmsOffSettingsScreen`), which, if Twill is still the default SMS app, also opens Android's default-apps screen, and when turned on restarts onboarding.
- **Efficiency notes:** chats page messages (`TwillProtocol.messages(chatId, limit)`, 100 at a time, more when scrolling up). Nostr's store bumps a per-chat counter so an open chat only re-reads its own messages. Nostr relay connections opened in the background ping every 3 minutes instead of 30 s (`NostrMessenger.backgroundOkHttp`). APKs are arm64-v8a only (`abiFilters`).
- **Adding or upgrading a library:** add it to `gradle/libs.versions.toml`, push, then run `gh workflow run update-dependencies.yml -R jawsh207/twill --ref main`. It records checksums in `gradle/verification-metadata.xml` and regenerates `assets/licenses.html`, then commits both; pull before pushing again. New license types may need mapping in `buildSrc/.../SpdxPolicy.kt` and a copyright line in `messaging.licenses.gradle.kts`.
- **Reading CI errors:** logs aren't reachable from cloud sessions, but `.github/ci/gradle-report-errors.sh` turns failures into annotations: `gh api repos/jawsh207/twill/check-runs/<job id>/annotations`.
- **Search in a conversation:** shared UI in `ui/twill/search/TwillConversationSearch.kt`: `TwillConversationSearch` (query, newest-first `TwillSearchHit`s with a rank = how many newest messages must be loaded, older/newer, debounced search), `TwillSearchAction` (top-bar button), `TwillSearchTopBar` (replaces the top bar while searching), `LocalTwillSearch` + `withTwillSearchHighlight()` (highlight), `TwillSearchScrollEffect` (loads older messages until the match is in, then scrolls). SMS/MMS: `twill/SmsMessageSearch.kt` (SQL over messages/parts), hooked into upstream's `ConversationScreen.kt` (button via `LocalConversationTopBarExtraActions`, bar swap), `ConversationScreenContent.kt` (scroll effect, grows the window with `onLoadOlderMessages`) and `ConversationMessageText.kt` (highlight). Other protocols: `TwillProtocol.searchMessages` (Nostr: SQL in `NostrMessageStore.search`; Delta Chat: the core's `search_messages`), `TwillChatViewModel.search/ensureLoaded`, `TwillChatScreen`.
- **Delete from SMS notifications:** `twill/TwillSmsNotificationDelete.kt` (action builder + `TwillSmsNotificationDeleteReceiver`, registered in `AndroidManifest.xml`) deletes the messages a notification shows, then marks the conversation read. Added in `BugleNotifications.createMessageNotification` after Reply (and Download, which wins the third slot when present).
- **Theme (Settings-style system colours):** `ui/core/Theme.kt` uses `MaterialExpressiveTheme` (expressive motion; needs material3 1.5, pinned in `libs.versions.toml`) over the system dynamic scheme, remapped like GrapheneOS Settings by `withSettingsSurfaces()`: `background`/`surface`/`surfaceContainer` = page (system surface container), `surfaceContainerHigh` = `surfaceBright` (dialogs, incoming bubbles), rows/cards/menus/sheets use `surfaceBright` explicitly (M3's menu default would be the page colour), accent only for highlights. Use these roles, never hard-coded colours; a `Surface` with a custom colour needs `contentColor` (onSurface). Window: `Theme.Compose` in `values/styles.xml` + `values-night/styles.xml` with `@color/twill_window_background` (`res/values*/twill_colors.xml`, system_surface_container_light/_dark; minSdk 36, so no -v34 copies) and transparent system bars (edge to edge). Settings screens use `ui/appsettings/common/SettingsLazyColumn.kt` (a `LazyListScope` that groups rows into rounded `surfaceBright` cards: 16dp margins, 3dp gaps, 24dp outer / 4dp inner corners; items with `contentType = SettingsGroupBreak` end a group, `SettingsGroupTitle` are drawn on the page; inside a card `surface` = card colour so ListItems blend in). Check against system Settings with `.github/workflows/screenshots.yml` (manual: emulator, light/dark × Other colors/Wallpaper colors, colour report; results on the `screenshots` branch, `git fetch origin screenshots`).
- **Home screen widgets:** rebuilt by Twill in `widget/` (upstream's Java widgets, list services and their images are gone). `TwillWidgets` draws both with RemoteViews + `RemoteCollectionItems` (no services) in the app's roles (`res/values*/twill_widget_colors.xml`, `twill_widget_*` drawables and layouts; previews are `android:previewLayout`s): "Conversations" (`BugleWidgetProvider`, every protocol, newest first, grouped cards) and "Conversation" (`WidgetConversationProvider`, one chat's messages; picked in `ui/conversationpicker/host/widget/WidgetPickConversationActivity.kt`, stored by `WidgetConversationPrefs` as `WidgetChatKey.encode()`: plain SMS id, or `twill:<protocol>:<chatId>`). Upstream class names and notify methods are kept, so placed widgets and upstream's data hooks keep working. `TwillWidgetData` reads SMS from the content provider and other protocols from `TwillProtocol.chats/messages` (no network). Updates: SMS hooks → `requestUpdate` (debounced), `TwillWidgets.watch` (started by `TwillRuntime.start` and widget updates) follows protocol chat lists while widgets exist. Taps go to `MainActivity` with the SMS conversation extra or `TwillNotifications.EXTRA_PROTOCOL/EXTRA_CHAT_ID`. The screenshots workflow places both widgets and captures them.
- **Long SMS as MMS:** `datamodel/MessageTextStats.java` marks any multi-part SMS as needing MMS when the pref is on.
